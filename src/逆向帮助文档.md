# MemeSense Payload 逆向帮助文档

最后更新: 2026-10-23
配套文档: `core/README.txt` (实现细节)、`开发技术文档.md` (工程状态)
本文件回答一个问题: **换一个 dump、换一台机器, 怎么把那些硬编码的值重新算出来。**

---

## 0. 先搞清楚手里三条数据链

逆向这个 payload 时, 同一个地址会在三种坐标系里出现, 混用必错。

| 坐标系 | 含义 | 怎么得到 |
|---|---|---|
| 文件偏移 | 在 payload_fix.bin / payload.bin 里的第几字节 | xxd / IDA 的 file offset |
| RVA | 相对镜像基址的偏移 = 节表 VirtualAddress + 节内偏移 | 由文件偏移换算, 或符号解析 |
| VA | 运行时绝对地址 = 模块基址 + RVA | 只在某个具体进程里成立 |

关键事实:

* payload.bin 是**内存 dump**, 文件偏移 == RVA。
* payload_fix.bin 是 pe_unmapper 转出的**标准 PE**, 文件偏移 != RVA, 靠节表换算。
* .brdata 里存的是 **VA**, 而且是"dump 那台机器 + dump 那个进程"的 VA。
  它既不是 RVA 也不是文件偏移, 这就是所有麻烦的根源。

换算工具 (只读, 不执行 payload):

```python
import pefile
p = pefile.PE("binary/payload_fix.bin")
def rva_to_off(rva):
    for s in p.sections:
        span = max(s.Misc_VirtualSize, s.SizeOfRawData)
        if s.VirtualAddress <= rva < s.VirtualAddress + span:
            return s.PointerToRawData + (rva - s.VirtualAddress)
    return None
```

## 1. 原始 ntdll 指针是怎么来的

.brdata 的 [2]..[7] 六个槽位, 存的全是 dump 进程里 ntdll 的绝对地址。
以本工程为例 (dump 自 Win10 22H2):

| 槽位 | 名字 | captured (VA) | dump ntdll 基址 | 推导 RVA |
|---|---|---|---|---|
| [2] | RtlRegisterThreadWithCsrss +0x80 | 0x00007FFCF22C4590 | 0x00007FFCF2270000 | 0x54590 |
| [3] | RtlInsertInvertedFunctionTable | 0x00007FFCF22808F0 | 同上 | 0x108F0 |
| [4] | LdrpModuleBaseAddressIndex | 0x00007FFCF23DD4A8 | 同上 | 0x16D4A8 |
| [5] | LdrpHeap | 0x00007FFCF23DC520 | 同上 | 0x16C520 |
| [6] | RtlRbInsertNodeEx | 0x00007FFCF2297DC0 | 同上 | 0x27DC0 |
| [7] | LdrpVectorHandlerList +8 | 0x00007FFCF23F13F0 | 同上 | 0x1813F0 |

dump ntdll 基址 0x7FFCF2270000 不是猜的, 而是从 dump 里**验证**出来的:

1. 在 dump 中找到 ntdll 的 PE 头 (若给的是完整进程 dump, 模块表就在 PEB->Ldr)。
2. 拿槽位 captured 减去候选基址, 得到 RVA。
3. 在该 RVA 处反汇编, 看是否是一个合理的函数序言 / 数据结构。

以 [2] 为例: 0x7FFCF22C4590 - 0x7FFCF2270000 = 0x54590。
在 dump 的 ntdll 里, 0x54590 处应当能对上 RtlRegisterThreadWithCsrss 的函数体。

**为什么需要 +0x80 / +0x08 这种 delta**: 槽位存的不是函数入口, 而是函数体内部
某个字段的地址。所以重建时必须 新基址 + 新RVA + delta, delta 是跨版本稳定的
(同一函数内部的相对偏移), RVA 不跨版本稳定。

### 1.1 换了一个 dump, 怎么重新求这些值

三种办法, 按可靠性排序:

**办法 A: 用 PDB (推荐)**

当前 ntdll 的 PDB 能给出**当前系统**的 RVA。工程里 init.cpp 的 InitPdbMap()
已经在做这件事:

```
%TEMP%\MemeSense_Symbols\<SymbolServerKey>\ntdll.pdb
SymbolServerKey = GUID(8+4+4) + Age(十六进制)
```

SymLoadModuleExW 必须传 **PDB 路径** 且 **基址非 0** (工程里固定 0x10000000),
否则 DbgHelp 返回成功但零符号。RVA = si.Address - si.ModBase。

**办法 B: 从 IAT 反推 dump 基址**

imports_fix.h 里每一项都是"dump 时解析好的绝对地址"。对同一模块:

```
delta    = liveExport - capturedIat      (同一台机器重新 dump 时成立)
dumpBase = liveModuleBase - delta
```

工程里 DeriveDumpBases() 就是干这个的, 对每个模块取众数并要求严格多数。
跨 Windows 版本时导出 RVA 会变, delta 会散开, 函数会自动拒绝并回退。
这时候用办法 C。

**办法 C: 手动指定**

```
set MEMESENSE_DUMP_NTDLL=0x7FFCF2270000
set MEMESENSE_DUMP_SDL3=0x7FFC2B0E0000
```

这两个值直接覆盖反推与常量, 是"我知道 dump 机器的基址"时的最直接手段。

### 1.2 一个必须记住的坑

**不能用当前 ntdll 的 PDB RVA 去校验 captured 值。** 实测:

```
RtlRegisterThreadWithCsrss
    dump (Win10 22H2) : 0x54590
    本机 (26100.9549) : 0xEF2E0
```

同一个函数, 跨版本 RVA 差了一大截。captured 只能用来判断"这个槽位原始值有没有
被破坏", 不能当成当前系统的地址。

## 2. SDL3 的两个槽位没有符号名, 怎么办

槽位 [0] 0x259、[1] 0x261 是 sdl3 的指针, 表里 symbol == nullptr。
原始做法是"按旧基址平移":

```
新地址 = 新 sdl3 基址 + (captured - dump sdl3 基址)
       = 新 sdl3 基址 + 相对偏移
```

其中 dump sdl3 基址 = 0x00007FFC2B0E0000。相对偏移分别是:

```
[0] 0x00007FFC2B379A78 - 0x00007FFC2B0E0000 = 0x299A78
[1] 0x00007FFC2B153A70 - 0x00007FFC2B0E0000 = 0x73A70
```

如果换 dump 但 sdl3 版本相同, 这两个相对偏移不变, 只需要换 dump sdl3 基址。
sdl3 版本变了就得重新定位: 在 dump 的 sdl3 里找出这两个地址属于哪个数据/函数,
再在新 sdl3 里按同样的特征 (字节序列、导出表位置、字符串引用) 重新定位。

工程里的保护: 算出的新地址必须落在目标进程 sdl3 的映射范围内, 否则跳过并报
"computed ... is outside live sdl3.dll"。所以即使偏移错了也不会写坏内存, 只是
那两个槽位不生效。

## 3. 重新生成 imports_fix.h

imports_fix.h 是 149 条 { IAT所在RVA, 模块名, 序号, 函数名 }。

### 3.1 为什么不能直接搬 payload 的导入表

payload 的导入表在 dump 里已经被解析成绝对地址了, 原始的名字/序号表可能已被
VMP 抹掉。所以这份表是**逆向重建**出来的, 不是从 PE 结构里读出来的。

### 3.2 重建步骤

1. **找 IAT 范围**。在 IDA 里看 payload.bin 的 .rdata (VA 0x15D000 起),
   搜一串连续的、高位是 0x00007FFC... / 0x00007FFF... 的 8 字节值。
   本工程的范围大约在 RVA 0x1CFAC0 ~ 0x1CFF98。
2. **逐项判定来源**。对每个 IAT RVA 的值 v:
   - 若 v 落在 dump 的某个模块范围内, 说明它来自该模块。
   - 用模块基址算出 v - moduleBase, 在 dump 的该模块里反查导出:
     按名导出直接读导出名表; 按序号导出就是序号。
   - 本工程的结果: ntdll 34、tier0 61、v8 25、libfreetype-6 12、
     v8_zlib 8、sdl3 6、msvcp_win 2、ucrtbase 1, 合计 149。
3. **写成表**。每行 { 0x1CFAC0, "ntdll.dll", 0, "KiUserExceptionDispatcher" }。
   序号导出写 { 0x1CFC00, "v8.dll", 682, "" }。
4. **核对总数**。日志里 "IAT Fix: repaired N/149" 必须是 149/149
   (目标进程模块齐全的前提下)。

### 3.3 换 payload 版本时

IAT 的 RVA 几乎一定变。不要改旧值, 重新做一遍 3.2。判断"变没变"的最快方法:
跑一次 InspectPayloadForHost, 它会把 IAT 槽位越界的项直接列出来。

## 4. .pdata 是诱饵, 不要注册

.pdata 在 RVA 0x1F1000, 只有 0x78 字节, 12 条 RUNTIME_FUNCTION。
看起来合理, 但 UNWIND_INFO 是假的:

```
entry[0]  (0x77860)  op = 0x0d, 0x0b, 0x07, 0x0c, 0x0e ...
                     -> 没有一个是合法 UWOP, 且 code offset 不递减
entry[10] (0x1F5000) 五个 PUSH_NONVOL 全在 offset 0x00
```

把它交给 RtlAddFunctionTable 后, 任何异常都会走 RtlVirtualUnwind 用垃圾恢复
RIP/RSP。实测会跳到 0x666600001001 (in eax, dx, 根本不是指令边界) 且线程
永不返回。所以 MS_REGISTER_EH 必须保持 0, 让 VMProtect 在 VM 初始化时装它
自己的表。

判断一张 .pdata 是不是诱饵的快速办法: 遍历每条 RUNTIME_FUNCTION, 检查

* BeginAddress < EndAddress <= SizeOfImage
* UnwindData 在镜像内
* UNWIND_INFO 的 Version 是 1 或 2
* 每条 UWOP 的 CodeOffset 严格递减

任何一条不满足, 就是诱饵或损坏。

## 5. PEB->Ldr 注册的硬约束 (换系统要重新核对)

payload 的异常处理器 (RVA 0x5380) 调 LdrFindEntryForAddress, 要求返回项的
DllBase == 自身基址, 否则 SEH/CRT 初始化在 0x553D 放弃。

LdrFindEntryForAddress 走的是 LdrpModuleBaseAddressIndex 这棵 RTL_RB_TREE,
不是 InLoadOrderLinks。本机 (10.0.26100.9549) 反汇编得到的约束:

```
LdrFindEntryForAddress (RVA 0x53EC0)
    0x53EDD  lea rdx, [rax+0x18]           ; out entry
    0x53EE1  call LdrpFindEntryForAddress  ; RVA 0x30740
LdrpFindEntryForAddress (RVA 0x30740)
    0x307B9  mov rax, [tree+0x00]          ; Root
    0x307C0  mov rbx, [tree+0x08]          ; Min
    0x307C7  test al, 1                    ; Root bit0 = 整棵树与 tree 地址 XOR
    0x307E0  mov rcx, [rbx-0x98]           ; node -> DllBase
    0x307EC  mov eax, [rbx-0x88]           ; node -> SizeOfImage
    0x30820  mov rax, [rbx-0x30]           ; node -> DdagNode
    0x3082B  cmp dword [rax+0x18], -1      ; DdagNode 标记
RtlRbInsertNodeEx (RVA 0x440A0)
    0x440BC  test al, 1                    ; 同样的 XOR 标记
    movzx ebp, r8b                         ; RightChild 在 r8b, 不是 dl
```

对应实现要点 (都在 inject.cpp 的 RegisterModuleInLdr):

* 三条链表字段各自自链 (+0x00 / +0x10 / +0x20)。
* DdagNode.Modules 自链, +0x18 = 0xFFFFFFFF。
* 先二分找插入点, 再以真实 parent 调 RtlRbInsertNodeEx。
* 桩签名: Tree=rcx, Parent=rdx, RightChild=r8b, Node=r9。
* 插入后校验返回值 == Node, 再用真实导出做一次自检。

**换 Windows 大版本时必须重新核对 +0xC8 / -0x98 / -0x88 / -0x30 这些偏移**,
它们属于 ntdll 内部结构, 没有稳定性保证。核对方法就是上面这套反汇编。

## 6. 符号服务器 key 的正确拼法

init.cpp 从磁盘 ntdll 读 CodeView (RSDS) 记录:

```
偏移 0   : "RSDS"
偏移 4   : GUID (16 字节)
偏移 20  : Age (4 字节)
偏移 24  : PDB 文件名 (ASCII, 以 0 结尾)
```

Symbol Server key 的格式:

```
%08X%04X%04X%02X%02X%02X%02X%02X%02X%02X%02X%X
  Data1 Data2 Data3 Data4[0..7]                    Age
```

**Age 必须用十六进制。** 用十进制拼时, age 超过 9 就会指向错误的文件。
下载 URL:

```
https://msdl.microsoft.com/download/symbols/<pdbname>/<key>/<pdbname>
```

缓存路径 %TEMP%\MemeSense_Symbols\<key>\<pdbname>, 按 key 分目录是为了
Windows 更新后自动产生新缓存。旧实现"文件非空就复用"会导致系统更新后继续用
旧符号算 RVA。

## 7. 校验服务 (server_src) 的协议常量

payload 会连本地校验服务, 逐字节比对回包。回包固定 28 字节:

```
1C 00 00 0B  00 00 00 00 ... (共 24 个 0)
```

改动任何一个字节都会导致 payload 拒绝继续。握手用两个命名事件:

```
Local\MemeSense_ServerReady    监听建立后 SetEvent
Local\MemeSense_Handshake      首个通过校验的探测后 SetEvent
```

两者都是 manual-reset, 只有首次成功探测会置位 Handshake。

## 8. 逆向时的推荐工作流

```
1. 拿到新 dump
   -> 先跑 tools/make.bat 生成 payload_fix.bin
   -> IDA 打开 payload_fix.bin (按 PE 分析, 不是 raw)

2. 确认布局
   -> src.exe 跑一次, 看日志 "Payload self-test: file=0x... image=0x..."
   -> 失败说明 make.bat 没做或 dump 不完整

3. 重建 IAT
   -> 按第 3 节, 得到新的 imports_fix.h
   -> 重跑, 看 "IAT Fix: repaired 149/149"

4. 重建 .brdata
   -> 按第 1 节确定 dump 模块基址 (PDB / IAT 反推 / 手填环境变量)
   -> 按第 2 节处理 sdl3
   -> 重跑, 看 "BrdataFix: repaired 8/8"

5. 处理加载器状态
   -> 需要时开 MS_REGISTER_LDR=1, 看自检行
   -> 异常相关一律 MS_REGISTER_EH=0

6. 定位剩余崩溃
   -> 看 "=== ENTRY RESULT ===" 与 "PEB->Ldr entry"
   -> 二分: 用 MS_ENTRY_SKIP=N 跳过入口前 N 字节定位出错指令
```

## 9. 已知未解问题 (截至 2026-10-23)

* payload 在 VM 初始化阶段仍可能以 C0000005 结束, 崩溃点与 RtlAllocateHeap
  相关。交接文档里记录的判断是: VMP 对 [4]/[5] 的地址范围存在校验, 而当前
  做法是写入真实的 LdrpModuleBaseAddressIndex / LdrpHeap, 不再是伪造区域。
* utils/ezpdb.hpp 未被任何 TU 包含, 与 init.cpp 的 PDB 逻辑重叠。
  若要合并, 需先修它自身三处问题: Age 用十进制、CodeView 没做
  RVA->文件偏移、SymSetOptions 在 SymInitialize 之后调用。
* RtlInsertInvertedFunctionTable 不是导出符号, 只有 PDB 能给出 RVA,
  该值已用 PDB 交叉验证, 但函数行为未做运行时验证。
